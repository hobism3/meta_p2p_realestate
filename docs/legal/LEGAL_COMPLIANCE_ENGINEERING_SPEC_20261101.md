# DirectHome 규제 대응 개발 명세 — 2026-11-01 (검토용)
> [법률 심층 분석](LEGAL_DEEP_DIVE_20261101.md) · [OPEN 이슈 원장](LEGAL_ISSUES_20261101.md)
> **구현 지시/설계안이지 법률 적합성 인증이 아님.** 매물 광고/게시자 확인에 관한 일부 규정은 2026-12-17/2027-06-17 시행 예정이며 대통령령 상세는 추후 대조 필요.

## I. 거래·알선 경계 (LEG-01)
현재 '허용 후보'는 사용자가 자기 매물의 정보를 입력하고, 상대방과 직접 소통하며, AI가 **기존 공개 정보**에 근거해 안내하거나 거래방의 진술을 정리하는 범위. 아래는 **법무 확정 전 비활성**:
- 플랫폼이 제시하는 가격 절충안/최적 거래조건, 자동 상대방 제안·승낙, 임대인 대신 계약 약속
- 거래 성사/계약 금액에 비례한 보수 수취, 거래 보증과 escrow 유사 표현
- 플랫폼이 중개업자처럼 매물을 추천하고 협상 당사자로 개입하거나 서명/권리 확인을 대신 수행
최종 판단은 사업자·유상성·반복성·실제 대리행위·광고/중개 사용 흐름·관련 판례 전체를 법률 전문가가 평가해야 함.

**판정 매트릭스(법무 기입)**: 기능 ID | 임대인/방문자/플랫폼 행위 주체 | 누구의 요청 | AI 재량 여부 | 누가 거래 의사 결정 | 수익 과금 기반 | 위험 판단 근거 | 필요한 동의·고지 | 법무 서명.

## II. 게시자 본인·관계 검증/광고 (LEG-04/07)
### 제안 데이터 모델 (아직 구현 안 됨)
- `listing_status`: `draft | pending_review | published | suspended | archived`
- `identity_check_status`: `unverified | pending | verified | rejected | expired`
- `property_relation_type`: `owner | co_owner | delegated_agent | landlord_non_owner | other | unknown`
- `relation_check_status`: 별도 `unverified | pending | verified | rejected | expired`
- `checked_at`, `expires_at`, `verification_method_code` (개인정보를 담지 않는 코드만)
- `policy_version`, `moderation_reason_code`, `moderated_at`, `audit_actor` 
- 근거 자료는 인증 벤더/암호화 저장소가 관리; 필요 최소한의 reference와 상태만 저장. **주민등록번호 DB 적재 금지**, 예외적으로 법률상 허용되는 경우 별도 법무 검토.
- 계정 `owner_id`는 서비스 DB의 *게시 계정*일 뿐 등기상 소유자가 아님; UI에 실소유자 검증으로 표시하지 않음.

### API / UX
1. 가입·로그인: '이용자 계정 로그인'과 '법적 본인 확인'을 다른 단계로 표현.
2. 매물 등록: 게시자가 적법한 게시 권한이 있다고 스스로 확인하는 **진술**과 독립적인 **검증완료**를 분리. 진술만으로 verified 승격 금지.
3. 게시 전: 매매/전세/월세 각 필수정보 validation + 공개 범위/정확성 체크. 소재지·면적·가격, 시행령 추가항목 추후 반영.
4. 매물 상세: 확인 여부·주체·최종 확인일 및 미검증 표시, 반드시 '안전한 거래 보장'과 구별.
5. 신고: 유형(허위 매물/명의도용/권리관계/개인정보/기타), 접수번호, 운영자 상태 및 조치 기록. 데모 버튼만 눌러 '신고 접수' 표시 금지.
6. 2027 플랫폼 대응: 국토교통부의 모니터링 자료요구/추가정보 게시/시정 요청에 대응할 로그·법무 검토·기한/승인 절차(최소정보, 접근권한, 감사흔적).
7. 미검증 매물의 공개 정책(기본 비공개/시연 표시/등록 유보 등)은 실제 사업 범위와 법무 조언으로 확정, 신설 법령 시행 시점 이전이라도 이용자 오인을 예방.

**DB 마이그레이션 설계만 선행; 자동 'verified' 처리·허위 인증 표시 구현 금지.**

### 처리 기본 규칙
- 목적별 개인정보 처리 적법성 근거(동의 또는 해당 법적 근거)를 **실제 수집 전에** 확인.
- 주민등록번호 제24조의2 법정 예외 없는 수집 금지. 제3자(등기 권리자) 데이터는 업로드인 1인의 동의로 정당화 불가.
- 개인정보 처리가 필요하다면 서비스-수탁사 관계(위탁/제3자 제공) 분류, 처리방침·수탁사/국가/보유·삭제 및 국외이전 요건 사전 확인.
- 무기한 로그 보존, 원문 응답 저장, AI provider 전달 시 모든 대화 원문 수집을 기본값으로 삼지 않음.
- 개발/CI 로그와 브라우저 네트워크 탭·오류 추적에 PDF·대화 원문을 남기지 않을 것.
- 계정 삭제 요청, 거래 기록의 분쟁 보전 예외, 백업 보존과 실제 삭제 주기, 데이터 주체 권리행사 채널 필요.
- 개인정보 처리방침은 이름/사업자 연락처/실제 수탁자/국외이전 근거 등 미확정 값으로 공표하지 않음.

## IV. 조건 확인·전자적 의사표시
- `room_proposals.status=agreed`는 **동일 버전의 확인을 한 쌍**으로 의미를 제한. 전자계약·서명·대금 지급·확정일자 발급을 뜻하지 않음.
- 민법상 의사표시를 구성할 수 있는 **실제 대화의 법적 영향**을 배제할 수 없으므로 '그냥 시연이니 법적 효력이 전혀 없다' 식 문구 금지(합성 AI 시연은 별개).
- 사용자 인증 강도, 법적 대리권, 변경 내역/타임스탬프, 원문 보전 및 취소/재확인 프로세스는 별도 법률 검토.
- 일정: `owner_visit_bookings.confirmed` 만 앱 내 승인 상태; 실제 현장 방문·자금 이동과 혼동 금지.

## V. AI 투명성/자동 판단 제한
- 생성형 모델 사용 흐름: 대화 시작 전 AI 이용 고지 및 결과별 표시, AI 생성 이미지/실사 혼동 방지.
- 규칙 기반 집주인 응대는 AI/자동화라는 사용자 이해를 방해하지 않도록 표시. Meta 생성형 챗과 동일한 인가/법적 권한을 주장하지 않음.
- 집톡이의 거래 위험 평가와 법률 설명은 참고/근거/미확인 범위를 보여주고, 사기 없음·거래 안전함·등기 문제 없음 결론 금지.
