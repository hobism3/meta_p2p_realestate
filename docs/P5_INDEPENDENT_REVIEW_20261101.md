1. 개별 작업함과 매물별 대표 거래방 카드가 같은 업무를 반복 노출하던 문제: P5 화면에서 중복 카드 제거.
2. 필터 후 일치 항목이 없을 때 빈 영역으로 보이는 문제: 조건별 결과 건수 및 0건 안내 추가.
3. API 호출 실패 시 과거 업무 수치가 계속 보이던 문제: 오류 시 오래된 데이터 제거.
4. 기존 거래방 이동은 승인·답변·합의를 실행하지 않도록 유지.

## 남은 리스크와 우선순위
- **높음/운영**: 실제 서로 다른 Supabase 사용자 2명으로 전체 거래 시나리오 미검증. Mock Playwright 통과와 구분.
- **높음/보안·법률**: 소유권 인증, 개인정보 보관·삭제, 등기 PDF 업로드 마스킹/처리 정책, 계약 법적 효력 없음. 공개 서비스 전 별도 검토 필요.
- **중간/정확성**: 예약 120/문의 100/AI 실패 40 상한을 공유하므로 작업함 개수는 전체 DB의 정확한 미처리 총수가 아님. 큰 매물 운영자에는 집계 전용 query와 cursor 페이지 처리 필요.
- **중간/일관성**: 집주인 작업함, 예약 패널, 확인 요청 패널이 별도로 15초 poll 하므로 순간적인 건수 차이와 DB 조회 증가 가능. 추후 통합 API 또는 invalidation 이벤트로 통합.
- **중간/실패 처리**: AI 응대 오류/토큰·모델 비용의 운영 메트릭이 부족. Cron 매일 1회는 복구 SLA 보장이 아님.
- **중간/UX**: 거래방으로 이동하는 링크는 개별 업무 처리 위치와 다를 수 있음. 다음 단계에서 ID 기반 개별 항목 anchor와 즉시 처리/복귀 동선 개선.
- **낮음/UX**: 페이지 목록과 작업함이 많은 매물을 가진 집주인에게 길어질 수 있음. 섹션 접기/검색 및 모바일 점검 권장.

## 판정
기능 개발과 안정적 운영을 분리한다. CI pass는 PR 코드의 자동 검증 결과일 뿐 실제 Meta 응답 정확도나 개인정보/법률/운영 준비 완료를 의미하지 않는다. 사용자 요청에 따라 E2E는 참고하되 빌드/기본 회귀 검증과 권한·승인 안전성은 필수.
