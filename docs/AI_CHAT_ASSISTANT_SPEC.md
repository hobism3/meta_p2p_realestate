# 집톡이(AI 거래 정리 도우미) 스펙

## 1. 개요

- 집톡이는 거래방에 함께 있는 AI 캐릭터다.
- 역할은 대화 정리와 미확인 안내. 협상·판단·확정은 하지 않는다.
- 캐릭터 표기: 거래 정리 도우미. AI 공인중개사라는 표현 금지.
- 이 문서는 설계만 다룬다. 코드 구현 없음.

## 2. 현재 거래방 구조 분석

### 2.1 메시지 저장 구조

- 위치: `meta_p2p_realestate/web/lib/store.ts`의 `DealState`.
- 형태: `{ messages, visits, agreements }`. 매물 id별로 묶는다.
- 메시지: `{ id, author, text, createdAt }`. author는 항상 나다.
- 합의: `{ id, text, createdAt }`. 자유 텍스트다. 구조 없음.
- 방문: `{ id, date, time, status }`. 상태는 제안됨·수락됨·거절됨.
- id 생성: `Date.now`+난수. 충돌 가능성은 낮지만 유일성 보장이 없다.

### 2.2 localStorage 사용 범위

- 키 3개: 매물, 거래방, 체크리스트. 전부 이 브라우저에만 저장된다.
- 서버·DB 없음. 새로고침 유지용 그 이상이 아니다.

### 2.3 사용자 간 공유 가능 여부

- 불가능하다. 임대인과 임차인이 서로의 메시지를 볼 방법이 없다.
- author가 나 하나로 고정된 것도 이 때문이다.
- 집톡이의 전제(양측 대화를 읽는다)가 현재 구조에서는 성립하지 않는다.
- 결론: 집톡이 전에 공유 저장소(백엔드+DB)가 먼저 필요하다.

## 3. 집톡이 UI 위치

- 거래방 상단: 집톡이 요약 카드. 최신 조건 초안과 미확인 건수를 보여준다.
- 메시지 영역: AI 말풍선. 요청 시 또는 중요 변경 시에만 나타난다. 도배 금지.
- 합의 로그 옆: 조건별 양측 확인 상태(임대인 확인·임차인 확인).
- 체크리스트 옆: 미확인 사항 연결. AI 안내는 문구만, 체크는 사용자가 한다.
- 공통 문구: 초안이며 자동 합의가 아니다. 법적 안전·효력을 보장하지 않는다.

## 4. AI 조건 추출 데이터 모델

- ConditionDraft: `{ id, field, value, sourceMsgIds, confidence, status, version, createdAt }`.
- field 예시: 보증금, 월세, 관리비, 입주일, 수리 약속, 옵션, 특이사항.
- status: 초안만 존재. 확정 상태 없음(자동 합의 금지).
- 버전 이력: 조건이 바뀌면 새 버전 추가. 이전 버전 삭제 금지.
- 원문 근거: 모든 조건에 sourceMsgIds 필수. 근거 없는 조건 금지.

## 5. 변경·충돌·확인 상태 모델

- ChangeEvent: `{ conditionId, oldValue, newValue, msgId, createdAt }`.
- Conflict: `{ field, sideA, sideB, msgRefs }`. 양측 발언이 다르면 충돌로 표시한다.
- Confirmation: `{ conditionId, landlord: boolean, tenant: boolean }`.
- 확인은 각 당사자가 직접 누른다. AI가 대신 확인하지 않는다.
- 양측 확인이 끝나도 계약 확정이 아니다. 합의 로그일 뿐이다.

## 6. Muse Spark 연동 방식

- 호출은 서버에서만 한다. 키를 클라이언트에 두지 않는다.
- 경로는 `/api/ziptalk` 같은 서버 프록시로 둔다(MVP에 없음. 신설 필요).
- 입력: 마스킹된 대화·합의 로그와 매물 정보다. 개인정보·주민번호는 제거한다.
- 출력: ConditionDraft JSON과 미확인 목록. 정해진 스키마만 받는다.
- 금지 출력: 등급, 판단, 특약 문구, 법률 해석.
- 모르는 것은 미확인으로 둔다. 빈칸을 채우지 않는다.
- 미확정: 모델, 엔드포인트, 프롬프트, 스키마, 비용.

## 7. 필요한 백엔드·DB 구조

- users: 임대인·임차인 구분. MVP는 익명+별명도 가능하나 공유 식별자는 필요.
- listings(서버본): 현재 시드+브라우저 저장을 서버로 옮긴다.
- deal_rooms: 매물 연결, 당사자 2명.
- messages: `{ roomId, authorId, text, createdAt }`. 불변. 삭제 대신 취소 표시.
- condition_drafts: 4절 모델. 버전 이력 포함.
- confirmations: 5절 모델.
- checklist: 현재 브라우저 저장을 방 단위로 옮긴다.
- 미확정: 스택, 호스팅, 인증 방식.

## 8. 합성 대화 기반 테스트 설계

- 시나리오 4종: 정상 합의, 조건 변경, 양측 충돌, 미확인 잔류.
- 각 시나리오는 합성 대화 스크립트와 기대 추출 결과를 함께 둔다.
- 검증 항목: 조건 추출 정확도, 변경 탐지, 충돌 탐지, 미확인 목록, 근거 연결.
- 판단·특약 문구가 출력에 섞이지 않는지 negative 케이스로 확인한다.
- API 없이도 실행 가능한 목업 테스트를 먼저 둔다. 실제 API 테스트는 비용·키 확보 후.
- 테스트 데이터는 전부 합성 표시한다.

## 9. 법률 추가 검토 사항

- 캐릭터 명칭·소개 문구가 중개·법률 전문가로 오인되지 않는지.
- AI 요약이 묵시적 합의 증거로 쓰일 위험. 초안·미확정 문구 상시 표시.
- 오추출로 생긴 손해의 책임 고지. 보장하지 않는다는 문구.
- 대화 저장·AI 전달에 대한 양측 고지와 동의 절차.
- 확인 체크가 계약成立으로 오인되지 않는지.
- 상태: 전부 미확인. 자문 전에는 문구·동작을 보수적으로 둔다.

## 10. 1차 구현 범위 제안

1. 공유 저장소: 방·메시지 서버 저장과 양측 author 구분.
2. 집톡이 카드 UI 틀: 수동 정리 표시부터. AI 연결 없이 배치·문구 검증.
3. 조건 초안 모델과 버전 이력 저장.
4. Muse Spark 프록시와 합성 대화 테스트.
5. 양측 확인 상태와 미확인 안내.
